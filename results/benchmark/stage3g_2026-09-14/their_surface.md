## (a) Three actual tool descriptions

The exact full strings are in the linked [provider definitions](https://github.com/RomeroLab/BioDesignBench/blob/718e452e3f73f8be423e954b6c05f3aa3f42859c/biodesignbench/tools/protein_design_provider.py). A generative example, `design_sequence`, says “using ProteinMPNN” and distinguishes sequence design from de novo backbone design. A predictive example, `predict_structure`, says “Returns predicted PDB, pLDDT, and pTM scores.” A physics example, `energy_minimize`, says “using OpenMM with AMBER14 force field” and returns minimized coordinates, energy change and RMSD. The individual descriptions are concise and mostly name a mechanism and output; they do **not** claim a model score is experimental fitness. The server-side counterparts are in [reference server tool definitions](https://github.com/jasonkim8652/protein-design-mcp/blob/7a45f13d5c7667513f4b3cfc47e472f3209b1be1/src/protein_design_mcp/server.py).

## (b–d) Guidance, cross-references and composites

`ProteinDesignToolProvider.get_tool_definitions_*` emits the **same descriptions** in both modes; benchmark mode filters out three composites, while user mode exposes all of them. User mode additionally supplies a system guidance block with named category lists, ordered workflows, and explicit cross-tool pointers (for example a backbone-generation step leading to sequence design and then structure validation). Benchmark mode uses only minimal guidance. Thus cross-reference is chiefly **system guidance plus some descriptions that name other tools**, not a mode-specific rewrite of every atomic description. Our old guided surface had neither the same cross-tool guidance nor symmetric composites. [Mode filtering and guidance](https://github.com/RomeroLab/BioDesignBench/blob/718e452e3f73f8be423e954b6c05f3aa3f42859c/biodesignbench/tools/protein_design_provider.py#L576-L669).

The provider marks `design_binder`, `design_fold`, and `optimize_sequence` composite. The first two cross backbone generation → sequence design → structure prediction; the last loops mutation proposal, ESM-2 scoring and structure checking. This **spans functional categories**. The current reference MCP server marks a slightly different set (`design_binder`, `design_sequence`, `optimize_sequence`, `rosetta_design`), an implementation discrepancy we must not conceal. I did not find a tool literally named `predict_then_score`; the published equivalent is a sequence of named model calls inside a composite. [Provider composite set](https://github.com/RomeroLab/BioDesignBench/blob/718e452e3f73f8be423e954b6c05f3aa3f42859c/biodesignbench/tools/protein_design_provider.py#L581-L595), [server composite set](https://github.com/jasonkim8652/protein-design-mcp/blob/7a45f13d5c7667513f4b3cfc47e472f3209b1be1/src/protein_design_mcp/server.py#L43-L50).

The provider's user-mode category list is Structure Prediction, Design Pipelines, Analysis, Validation and Energy—not a literal four-way generate/predict/score/analyse taxonomy. Descriptions distinguish ESM-2 learned plausibility from OpenMM/Rosetta energy **by naming their mechanisms**, but I found no explicit `orthogonal` label in these provider tool descriptions. Therefore our scientific description can accurately tell the agent that learned and physical evidence are different channels; that would be **our clearer adaptation**, not a verbatim copy of theirs. [Provider category guidance](https://github.com/RomeroLab/BioDesignBench/blob/718e452e3f73f8be423e954b6c05f3aa3f42859c/biodesignbench/tools/protein_design_provider.py#L603-L648).

## (e) Agent loop and final-output contract

The released benchmark general-purpose loop issues provider function calls, appends tool results, iterates until the model emits a non-tool final message or a step/length limit, then collects output artifacts or design sequences. Its leaderboard runner sets a 50-step default and tells the model to end with a FASTA block, then **extracts sequences from final text**. It does not require an MCP `submit_answer` call. Our Codex pilot instead has an explicit record tool and one-submission contract; the Stage 3f record server failed to mount, so submission was structurally unavailable, and Codex's normal final message could not satisfy that contract. This is a harness difference, not evidence of a worse model. [Agent loop](https://github.com/RomeroLab/BioDesignBench/blob/718e452e3f73f8be423e954b6c05f3aa3f42859c/biodesignbench/agents/general_purpose/gpt5_tools.py), [leaderboard runner](https://github.com/RomeroLab/BioDesignBench/blob/718e452e3f73f8be423e954b6c05f3aa3f42859c/biodesignbench-leaderboard/eval_agent.py#L31-L54).

## (f) Forced depth

The public intervention template is [in `interventions.py`](https://github.com/RomeroLab/BioDesignBench/blob/718e452e3f73f8be423e954b6c05f3aa3f42859c/biodesignbench/interventions.py#L60-L91). It operationalizes the four verbs as **generate at least five independent candidates**, **evaluate each using at least four metric categories**, **rank across those metrics**, and **submit only the top three while recording every rejected candidate's metrics**. This is more concrete than the four-verb paraphrase in the request and is for design tasks, not W1's fixed variant list. We should adapt the structure, not copy its candidate counts into W1. A proposed W1-specific Arm 3F paragraph is in `our_surface_diff.md`; frozen pilot prompt files remain unchanged because the request also forbids changing scored prompts.
